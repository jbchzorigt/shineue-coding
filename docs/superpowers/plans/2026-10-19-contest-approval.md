# Contest Participation Approval Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** «Оролцох» becomes a request that a teacher/admin approves (per-contest setting); only approved participants see problems, submit, and appear in rankings.

**Architecture:** Two new columns on `contests` / `contest_participants` (Drizzle migration with defaults that keep old rows working). The DB layer in `src/lib/db/contests.ts` owns statuses; a small pure module `src/lib/contest-access.ts` holds the access message and request-scope selection, so they can be unit-tested; pages and the submit API read `participant.status`.

**Tech Stack:** Next.js 16.2 App Router (params/searchParams are Promises; read `node_modules/next/dist/docs/` before touching Next APIs), React 19, Drizzle 0.45 + Postgres, `node:test` via tsx.

**Spec:** `docs/superpowers/specs/2026-10-19-contest-approval-design.md`

## Global Constraints

- No commits or pushes. The user commits on "final code". Record progress in the ledger instead of committing.
- UI text is Mongolian; code, identifiers and comments are English.
- Status values are exactly `pending`, `approved`, `rejected`.
- `contests.requires_approval`: `boolean not null default true`.
- `contest_participants.status`: `text not null default 'approved'` with check `in ('pending','approved','rejected')`; `decided_by` text → `users.uid` `on delete set null`; `decided_at` timestamptz; index on `(contest_id, status)`.
- Only `isStaff` roles (teacher, admin) may decide requests.
- Exact Mongolian strings:
  - Pending card: «Хүсэлт илгээсэн — багш зөвшөөрөхийг хүлээж байна»
  - Rejected card: «Таны хүсэлтийг татгалзсан. Асуух зүйл байвал багштайгаа ярина уу.»
  - Submit API, pending: «Багш таны хүсэлтийг зөвшөөрөөгүй байна.»
  - Submit API, rejected: «Таны хүсэлтийг татгалзсан.»
  - Submit API, no row (unchanged): «Эхлээд тэмцээнд бүртгүүлнэ үү.»
  - Contest-list badges: «Бүртгүүлсэн» / «Хүлээгдэж байна» / «Татгалзсан»
  - Form checkbox: «Оролцоход багшийн зөвшөөрөл шаардах»
  - Empty request list: «Хүлээгдэж буй хүсэлт алга.»
- DB tests run serially: `npm test` already passes `--test-concurrency=1`. Single file: `npx tsx --env-file=.env.local --conditions=react-server --test <file>` (run DB test files one at a time).
- Never touch the `shineue-db` container or port 5432. Local dev DB is coding-db on 5433. Never print `.env.local` values.

## Review Focus

1. A forged form (uids from another contest, an unknown uid, a staff uid) passed to the decide action changes nothing outside this contest's matching rows → `decideRequests` test with an unknown uid and another contest's uid returns 0 and leaves the rows unchanged (Task 1).
2. A rejected student who re-posts the register action stays rejected and cannot slip to pending/approved → register-after-reject test (Task 1).
3. Class scope approves only that class's **pending** rows, not rejected ones and not students with no class → `requestUidsInScope` test (Task 2).
4. A teacher «Татгалзах» on a row another teacher already approved does not demote it → `decideRequests` reject-on-approved test (Task 1).
5. A pending participant is absent from the leaderboard, counts, CSV and the submissions filter (all via `listParticipants`) → `listParticipants` approved-only test (Task 1). Plus a browser check that a pending student opening a problem URL directly is redirected (Task 3).

**Interfaces:**
- Produces, in `src/lib/db/contests.ts`:
  - `Contest.requires_approval: boolean`
  - `export type ParticipantStatus = "pending" | "approved" | "rejected"`
  - `Participant.status: ParticipantStatus` and `Participant.registered_at: number` (epoch ms)
  - `export interface ContestRequest { uid: string; name: string | null; email: string; class_name: string | null; status: "pending" | "rejected"; requested_at: number /* epoch ms */ }`
  - `registerParticipant(contestId: string, user: { uid: string; name: string | null; email: string }): Promise<ParticipantStatus>`. On conflict it does nothing and returns the existing status.
  - `getParticipant(contestId, uid): Promise<Participant | null>`. Returns any status.
  - `listParticipants(contestId): Promise<Participant[]>`. Approved only, same ranking as today.
  - `listRequests(contestId): Promise<ContestRequest[]>`. Pending + rejected, `registered_at` ascending, with `users.class_name`.
  - `countPending(contestIds: string[]): Promise<Map<string, number>>`. Only ids with at least 1 pending row appear.
  - `decideRequests(contestId: string, uids: string[], decision: "approved" | "rejected", staffUid: string): Promise<number>`. Returns the number of rows changed. Approve affects `pending` and `rejected` rows; reject affects `pending` rows only. Sets `decided_by` and `decided_at = now()`. Runs as one UPDATE. An empty `uids` returns 0 without a query.
  - `applySubmissionScore` throws `NotFoundError("Багш таны хүсэлтийг зөвшөөрөөгүй байна.")` when the locked row's status is not `approved`, before inserting the submission.

- [ ] **Step 1: Update fixtures and write the failing tests in `src/lib/db/contests.test.ts`**

Fixtures:
- Give the existing `contest` fixture `requires_approval: false` so the current tests keep their meaning.
- Add `const gated: Contest = { ...contest, id: "gated-cup", requires_approval: true }`.

- Update the existing `getParticipant` deepEqual (≈line 116) to include `status: "approved"`, and assert separately that `registered_at` is a number.

New tests (names and assertions):
- `registration needs approval when the contest asks for it`: `registerParticipant(gated.id, s1)` returns `"pending"`, and `getParticipant` gives `.status === "pending"`. On `contest`, the result is `"approved"`.
- `registering again never changes the status`: register on `gated`, then `decideRequests(gated.id, ["s1"], "rejected", "t1")`, then register again. The second call returns `"rejected"` and the status stays `"rejected"`.
- `only approved participants are listed and ranked`: on `gated`, a and b register, and only a is approved. `listParticipants` uids are `["a"]`. `listRequests` gives `[{ uid: "b", status: "pending", class_name: <b's class> }]`, and `requested_at` is a number.
- `approve moves pending and rejected rows; reject only pending`:
  - Set up three users: p (pending), r (rejected), ok (approved).
  - `decideRequests(id, ["p", "r"], "approved", "t1")` returns 2.
  - Make p pending again via a fresh user. `decideRequests(id, ["ok"], "rejected", "t2")` returns 0, and ok stays `"approved"`.
  - Rows decided by t1 have `decided_by === "t1"`. Read them from `contestParticipants` directly, and check that `decided_at` is not null.
- `decide ignores uids outside the contest`: on a second gated contest, `decideRequests(gated.id, ["ghost", <uid registered only in other contest>], "approved", "t1")` returns 0, and the other contest's row stays `"pending"`.
- `countPending counts per contest`: two gated contests with 2 and 0 pending rows give `Map` entries `[[id1, 2]]`.
- `a pending participant cannot score`: `applySubmissionScore` on a pending row rejects with `NotFoundError`, and `contestSubmissions` has 0 rows.
- `requires_approval round-trips`: `upsertContest(gated)` then `getContest(gated.id)` gives `requires_approval === true`. Upserting with `false` reads back `false`.

The test users t1/t2 must exist (`addUser("t1", { role: "teacher" })`) because `decided_by` has an FK.
