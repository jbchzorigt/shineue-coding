### 📖 Гол ойлголт

**Схем (schema)** бол өгөгдлийн сангийн бүтцийн загвар: ямар хүснэгт, талбар, өгөгдлийн төрөл, түлхүүр байх, өгөгдөл хоорондын хамаарлыг хэрхэн удирдахыг тодорхойлно. Схем бол **дизайн**, өгөгдөл өөрөө биш. Excel-ээр төсөөлбөл баганын нэрстэй толгой мөр нь схем, доорх мөрүүд нь өгөгдөл. A3.1 модульд дурдсан «хатуу схем» нь энэ бүтэц: өгөгдөл орсны дараа өөрчлөхөд хэцүү.

**Өгөгдлийн сангийн удирдлагын систем (DBMS)** өгөгдлийн санг үүсгэж, хадгалж, түүнд хэн яаж хандахыг хянадаг программ (A3.1). Энэ нь аппликейшн ба үйлдлийн системийн дунд ажиллаж, асуулга (query), маягт (form), тайлан (report), график гаргах хэрэгсэл санал болгоно. Схемийг DBMS хадгалж, түүний дүрмийг өгөгдөл бүрд мөрдүүлнэ.

```text
[Апп, вэб сайт] ──► [DBMS: схем, дүрэм] ──► [Үйлдлийн систем] ──► [Диск дээрх файл]
```

Хаалтан доторх нэр бүр нэг давхарга, сум нь хүсэлт дамжих чиглэл. Апп файлтай шууд ажилладаггүй — DBMS-ээр дамжина.

#### Схемийн гурван түвшин

Нэг борлуулалтын системийг гурван түвшинд харъя. Дээрээс доош илүү нарийвчилсан, нэг DBMS-тэй илүү холбоотой болно.

| Түвшин | Асуулт | Юу агуулах вэ | Борлуулалтын системд |
|---|---|---|---|
| Ойлголтын схем (conceptual schema) | Ямар өгөгдөл? | Биет, талбар, хамаарал — хийсвэр, ихэвчлэн ER диаграмаар (A3.2.2) | Хэрэглэгч, захиалга, бүтээгдэхүүн; «хэрэглэгч захиалга өгнө; захиалгад нэг ба түүнээс олон бүтээгдэхүүн орно» |
| Логик схем (logical schema) | Яг ямар бүтэц? | Хүснэгт, талбар, өгөгдлийн төрөл, үндсэн ба гадаад түлхүүр, хязгаарлалт; нормчилсон (A3.2.5); ямар ч DBMS-ээс хамаарахгүй | `Products(ProductID INTEGER [PK], ProductName VARCHAR, Price REAL)`; «үнэ сөрөг байж болохгүй» |
| Физик схем (physical schema) | Яг яаж хадгалах? | Нэг DBMS-ийн яг бичиглэл ба хэмжээ, индекс, хэсэглэлт, хадгалах төхөөрөмж, хандах арга | `ProductName VARCHAR(100) NOT NULL`; `ProductName` дээр индекс; Orders хүснэгтийг хэсэглэх |

- **Хязгаарлалт (constraint)** — өгөгдөлд тавих дүрэм: хоосон байж болохгүй, давтагдахгүй, үнэ сөрөг биш гэх мэт. A3.1-ийн лавлагааны бүрэн бүтэн байдал ч хязгаарлалт.
- **Индекс (index)** — номын ард байдаг нэр томьёоны жагсаалт шиг нэмэлт бүтэц: тухайн баганаар хайхад бүх мөрийг уншилгүй шууд олно.
- **Хэсэглэлт (partitioning)** — маш том хүснэгтийг (жишээ нь олон жилийн захиалга) тусдаа хэсгүүдэд хувааж хадгалах.

Логик схем **юу** байхыг (хүснэгт, талбар, ерөнхий төрөл, түлхүүр, дүрэм), физик схем түүнийг тухайн DBMS-д **яаж** хэрэгжүүлэхийг (яг бичиглэл, хэмжээ, индекс, хадгалалт) шийднэ. Эх сурвалжууд энэ хилийг яг ижил татдаггүй тул шалгалтад шийдвэрээ үндэслэлтэй бич.

#### Схем юунд тус болдог вэ?

| Давуу тал | Схем яаж тусалдаг вэ |
|---|---|
| Өгөгдлийн зохион байгуулалт (data organisation) | Өгөгдөл хаана, ямар бүтэцтэй хадгалагдахыг тодорхой болгоно |
| Өгөгдлийн аюулгүй байдал (data security) | Хэрэглэгч бүрийн эрх ба **харагдацыг (view)** тодорхойлно. Харагдац бол хүснэгтийн зөвхөн зарим мөр, баганыг үзүүлдэг «цонх»: сурагч зөвхөн өөрийн дүнг харна |
| Өгөгдлийн бүрэн бүтэн байдал (data integrity) | Хязгаарлалт өгөгдлийг зөв, нийцтэй байлгана: сөрөг үнэ, байхгүй хэрэглэгчийн захиалга орохгүй |
| Гүйцэтгэл (performance) | Физик схемд төлөвлөсөн индексээр асуулга хурдан ажиллана |
| Өргөтгөх боломж (scalability) | Ажиллаж буй аппуудыг эвдэлгүйгээр өгөгдлийн санг өөрчилж, томруулна |
| Харилцаа (communication) — сурах бичигт байхгүй нэмэлт | Менежер ойлголтын түвшнийг, хөгжүүлэгч логик ба физик түвшнийг уншина |

#### Алдааг олоорой: нэг захиалгад ганц бүтээгдэхүүн үү?

Сурах бичгийн логик схемд (х.175) `ProductID` нь Orders хүснэгт **дотор** гадаад түлхүүр болсон байдаг. Гэтэл ойлголтын схем «захиалгад нэг ба түүнээс олон бүтээгдэхүүн орно» гэдэг. Гадаад түлхүүр **ганц** утга хадгалдаг тул (A3.1) ийм схемээр захиалга бүр ганцхан бүтээгдэхүүнтэй болно. Захиалга ба бүтээгдэхүүн бодитоор m:m хамааралтай тул холбох хүснэгт хэрэгтэй:

```text
Customers (CustomerID [PK], LastName, FirstName, EmailAddress)
Products  (ProductID [PK], ProductName, Price)
Orders    (OrderID [PK], OrderDate, CustomerID [FK])
OrderLine (OrderID [PK, FK], ProductID [PK, FK], Quantity)
```

Тэмдэглэгээ A3.1 модульд үзсэнтэй ижил: хаалтын өмнө хүснэгтийн нэр, дотор нь талбарууд; `[PK]` — үндсэн түлхүүр, `[FK]` — гадаад түлхүүр, `[PK, FK]` — хоёулаа. OrderLine-ийн хоёр `[PK]` талбар хамтдаа нийлмэл түлхүүр. Сургамж: түвшин бүр дээд түвшнийхээ шийдвэртэй нийцэх ёстой. Сурах бичигт ч алдаа байж болно — шалгаж унш.

### 💻 Туршиж үзээрэй

Доорх `sales_schema.py` нь дээрх дөрвөн хүснэгтийг SQLite-д **физик схем** болгож үүсгээд, хязгаарлалт бүрийг зориуд зөрчиж үзнэ.

```python
import sqlite3

con = sqlite3.connect(":memory:")          # a new, empty database in memory
con.execute("PRAGMA foreign_keys = ON")    # SQLite checks foreign keys only when this is ON
con.executescript("""
CREATE TABLE Customers (
    CustomerID   INTEGER PRIMARY KEY,
    LastName     VARCHAR(100) NOT NULL,
    FirstName    VARCHAR(100) NOT NULL,
    EmailAddress VARCHAR(100) NOT NULL UNIQUE);
CREATE TABLE Products (
    ProductID   INTEGER PRIMARY KEY,
    ProductName VARCHAR(100) NOT NULL,
    Price       REAL NOT NULL CHECK (Price >= 0));
CREATE TABLE Orders (
    OrderID    INTEGER PRIMARY KEY,
    OrderDate  DATE NOT NULL,
    CustomerID INTEGER NOT NULL REFERENCES Customers(CustomerID));
CREATE TABLE OrderLine (
    OrderID   INTEGER REFERENCES Orders(OrderID),
    ProductID INTEGER REFERENCES Products(ProductID),
    Quantity  INTEGER NOT NULL CHECK (Quantity > 0),
    PRIMARY KEY (OrderID, ProductID));
CREATE INDEX idx_last_name ON Customers(LastName);
INSERT INTO Customers VALUES (1, 'Bold', 'Anu', 'anu@mail.mn'), (2, 'Dorj', 'Bat', 'bat@mail.mn');
INSERT INTO Products VALUES (10, 'Notebook', 2.5), (11, 'Pen', 0.8), (12, 'Calculator', 15.0);
INSERT INTO Orders VALUES (100, '2026-09-01', 1), (101, '2026-09-02', 2);
INSERT INTO OrderLine VALUES (100, 10, 3), (100, 11, 5), (101, 12, 1);
""")

rows = con.execute("""SELECT Orders.OrderID, Customers.FirstName, Products.ProductName, OrderLine.Quantity
                      FROM Orders JOIN Customers ON Orders.CustomerID = Customers.CustomerID
                                  JOIN OrderLine ON Orders.OrderID = OrderLine.OrderID
                                  JOIN Products ON OrderLine.ProductID = Products.ProductID
                      ORDER BY Orders.OrderID, Products.ProductName""").fetchall()
for order_id, name, product, quantity in rows:
    print(order_id, name, product, quantity)

attempts = [("Duplicate email (UNIQUE)", "INSERT INTO Customers VALUES (3, 'Tsend', 'Saraa', 'anu@mail.mn')"),
            ("Negative price (CHECK)", "INSERT INTO Products VALUES (13, 'Ruler', -1)"),
            ("Missing date (NOT NULL)", "INSERT INTO Orders VALUES (102, NULL, 1)"),
            ("Unknown customer (FOREIGN KEY)", "INSERT INTO Orders VALUES (103, '2026-09-03', 99)")]
for label, sql in attempts:
    try:
        con.execute(sql)
        print(label, "-> accepted")
    except sqlite3.IntegrityError:
        print(label, "-> rejected")
```

**Шинэ мөрүүд:** `NOT NULL` — хоосон байж болохгүй; `UNIQUE` — давтагдахгүй; `CHECK (Price >= 0)` — нөхцөл үнэн байх ёстой; `CREATE INDEX` — индекс үүсгэнэ (гаралтад харагдахгүй, хайлтыг хурдасгана). `PRIMARY KEY`, `REFERENCES`, `JOIN … ON`, `ORDER BY`-ийг A3.1 модульд үзсэн: энд гурван `JOIN` дөрвөн хүснэгтийн мэдээллийг нэг мөр болгож, `ORDER BY` эхлээд захиалгаар, тэнцвэл бүтээгдэхүүний нэрээр эрэмбэлнэ.

Гаралт:

```text
100 Anu Notebook 3
100 Anu Pen 5
101 Bat Calculator 1
Duplicate email (UNIQUE) -> rejected
Negative price (CHECK) -> rejected
Missing date (NOT NULL) -> rejected
Unknown customer (FOREIGN KEY) -> rejected
```

100-р захиалга хоёр бүтээгдэхүүнтэй — OrderLine-ийн ачаар. Дөрвөн буруу оруулалтыг дөрвөн өөр хязгаарлалт зогсоов. Одоо өөрөө шалга: кодын аль хэсэг нь логик шийдвэр, аль нь физик нарийвчлал вэ?

<details>
<summary>Хариу</summary>

Код бүхэлдээ физик схем: нэг DBMS-ийн (SQLite) яг бичиглэл. Дотроос нь **логик** шийдвэрүүдийг танина: хүснэгт ба талбарын нэр, `INTEGER`, `REAL`, `DATE` гэх ерөнхий төрөл, үндсэн ба гадаад түлхүүр, «үнэ сөрөг биш» гэх дүрэм. **Физик** нарийвчлал: `VARCHAR(100)`-ийн 100, `CREATE INDEX`, өгөгдлийн санг санах ойд (`":memory:"`) хадгалах.

</details>

<Callout type="warning">
**⚠️ Анхаарах зүйлс**

- **Схем ≠ өгөгдөл.** Схем бол хоосон хүснэгтүүдийн бүтэц, мөрүүд нь өгөгдөл. `'anu@mail.mn'` схемийн хэсэг биш.
- **Логик схем DBMS-ээс хамаардаггүй.** `VARCHAR(100)`-ийн хэмжээ, индекс, хадгалах диск гэх мэт нэг DBMS-ийн нарийвчлал физик түвшинд хамаарна.
- **Түвшин бүр дээд түвшнийхээ шийдвэртэй нийцэх ёстой.** «Олон бүтээгдэхүүн» гэсэн ойлголтын дүрмийг логик схем ганц гадаад түлхүүрээр эвдэж болохгүй.
- **SQLite-д `VARCHAR(100)`-ийн урт шалгагддаггүй.** PostgreSQL зэрэг ихэнх DBMS 100-аас урт текстийг татгалзана. Дэлгэрэнгүйг A3.2.3-т.

</Callout>

### 📝 Түлхүүр нэр томьёо

## A3.2.2 ER диаграм: cardinality ба modality

> 🎯 **Зорилго:** **Construct** ERDs — нөхцөлд тохирсон ER диаграм зохиож зурах. Энэ хэсгийн төгсгөлд та:
>
> - ER диаграмыг өгөгдлийн сан зохион бүтээхэд яагаад ашигладгийг тайлбарлана;
> - Хэрээний хөл тэмдэглэгээний дөрвөн төгсгөлийг уншина;
> - Cardinality (дээд тоо) ба modality (доод тоо)-г ялгана;
> - Өгөгдсөн нөхцөлөөр биет, талбар, түлхүүр, хамаарал бүхий ER диаграм зохионо.

2. Нэг онгоц — олон нислэг. Энэ ямар хамаарал вэ?
3. m:m хамаарлыг яагаад шууд хадгалж чадахгүй вэ?
4. Онлайн дэлгүүрт хэрэглэгч бүр дор хаяж нэг захиалга өгсөн байх ёстой юу? Захиалга бүр хэрэглэгчтэй байх ёстой юу?

<summary>Хариу</summary>

### 📖 Гол ойлголт

**ER диаграм (entity-relationship diagram, ERD)** бол өгөгдлийн сангийн биетүүд ба тэдгээрийн хоорондын хамаарлыг харуулсан зураг. Ойлголтын схемийг (A3.2.1) харуулах хамгийн түгээмэл арга.

- Хэрэглэгч, менежер, хөгжүүлэгч бүгд уншдаг нийтлэг «хэл» болж, оролцогч талуудын харилцааг сайжруулна.
- Дизайныг баримтжуулж, хожим хөгжүүлэх, засварлахад тусална.
- Хамаарал ба хязгаарлалт тодорхой зурагдсан тул өгөгдлийн бүрэн бүтэн байдал, нийцтэй байдлыг хангахад тусална.

#### Биетийн хайрцаг

```text
┌──────────────────┐
│ Orders           │
├──────────────────┤
│ OrderID     [PK] │
│ OrderDate        │
│ CustomerID  [FK] │
└──────────────────┘
```

Дээд хэсэгт биетийн нэр, доор нь талбарууд (attribute). Түлхүүрийг A3.1-ийн `[PK]`, `[FK]` тэмдгээр тэмдэглэнэ; цаасан дээр үндсэн түлхүүрийг ихэвчлэн доогуур нь зурдаг. Доорх жишээнүүдэд зай хэмнэхийн тулд хайрцгийн оронд биетийн нэрийг л бичнэ.

#### Хэрээний хөл тэмдэглэгээ (crow's foot notation)

Хоёр биетийг шугамаар холбож, шугамын үзүүр бүрт **хоёр** тэмдэг тавина. Энэ хичээл зургийг текстээр зурдаг тул тэмдгийг `o`, `|`, `<` (эсвэл `>`) тэмдэгтээр бичнэ; цаасан дээр `<` нь гурван салаатай «хэрээний хөл» болно.

```text
Шугам (B-ийн үзүүр)   Утга              Хамгийн багадаа   Хамгийн ихдээ
A ──────────|| B      яг нэг            1                 1
A ──────────o| B      тэг эсвэл нэг     0                 1
A ──────────|< B      нэг эсвэл олон    1                 олон
A ──────────o< B      тэг эсвэл олон    0                 олон
```

- **Биетэд ойр (дотор) тэмдэг = хамгийн ихдээ:** `|` — нэг, `<` — олон.
- **Биетээс хол (гадна) тэмдэг = хамгийн багадаа:** `o` — тэг (заавал биш), `|` — нэг (заавал).
- **Уншихдаа** нэг биетээс эхэлж, шугамыг даган **нөгөө үзүүрт** очиж, тэнд байгаа тэмдгийг унш. Зүүн талын биетийн үзүүр толин тусгал болно: `||`, `|o`, `>|`, `>o`.

```text
Customers ||──────o< Orders
```

- Нэг **хэрэглэгчээс** уншвал → Orders-ийн үзүүрт `o<`: хэрэглэгч **тэг эсвэл олон** захиалга өгнө.
- Нэг **захиалгаас** уншвал → Customers-ийн үзүүрт `||`: захиалга **яг нэг** хэрэглэгчтэй.

#### Cardinality ба modality

| | Cardinality (дээд тоо) | Modality (доод тоо) |
|---|---|---|
| Асуулт | Нэг бичлэгтэй нөгөө биетийн **хамгийн ихдээ** хэдэн бичлэг холбогдох вэ? | **Хамгийн багадаа** хэд вэ — холбоо заавал уу? |
| Утга | Нэг эсвэл олон; үүнээс хамаарлын төрөл (1:1, 1:m, m:m) гарна | 0 — заавал биш (optional), 1 — заавал (mandatory) |
| Тэмдэг | Дотор тэмдэг: босоо зураас эсвэл хэрээний хөл | Гадна тэмдэг: `o` эсвэл босоо зураас |
| Жишээ | Нэг хэрэглэгч олон захиалга өгч болно | Шинэ өвчтөнд эмчилгээний бүртгэл хараахан байхгүй байж болно (заавал биш); онлайн дэлгүүрт захиалга бүр хэрэглэгчтэй (заавал) |

#### Жишээ: борлуулалтын системийн ERD

```text
Customers ||──o< Orders ||──|< OrderLine >o──|| Products
```

| Шугам | Нэг талаас | Нөгөө талаас |
|---|---|---|
| Customers — Orders | Хэрэглэгч тэг эсвэл олон захиалга өгнө | Захиалга яг нэг хэрэглэгчтэй |
| Orders — OrderLine | Захиалга нэг эсвэл олон мөртэй | Мөр бүр яг нэг захиалгад хамаарна |
| Products — OrderLine | Бүтээгдэхүүн тэг эсвэл олон мөрөнд орно | Мөр бүр яг нэг бүтээгдэхүүнийг заана |

Orders ба Products хоорондоо m:m хамааралтай; ERD-д OrderLine холбох хүснэгт (A3.1) үүнийг хоёр 1:m болгосон. Шугам бүрийг хоёр чиглэлд нь уншиж хэвших нь шалгалтад хамгийн их тусална.

#### ERD-ээс хүснэгт рүү

- **1:m** → «олон» талын хүснэгтэд гадаад түлхүүр: `Orders.CustomerID`.
- «Нэг» талын үзүүр `||` (яг нэг, заавал) бол гадаад түлхүүр хоосон байж болохгүй (`NOT NULL`); `o|` (тэг эсвэл нэг) бол хоосон (`NULL`) байж болно.
- **m:m** → хүснэгт үүсгэхээс **өмнө** холбох хүснэгтээр задал.

#### Дасгал: сургуулийн эмчийн өрөө

Эмчийн өрөө сурагч (STUDENT), сувилагч (NURSE), үзлэгийг (VISIT) бүртгэнэ. Үзлэг бүр нэг сурагчийнх, түүнийг нэг сувилагч хийнэ. Нэг үзлэгээр хэд хэдэн эм (MEDICINE) өгч болно, огт өгөхгүй ч байж болно; нэг эмийг олон үзлэгт өгнө.

1. Биет бүрийн 2–3 талбар ба үндсэн түлхүүрийг бич.
2. Хамаарал бүрийг хэрээний хөлөөр зур: cardinality ба modality хоёуланг нь.
3. m:m-ийг холбох хүснэгтээр задал. Шугам бүрийг хоёр өгүүлбэрээр унш.

<details>
<summary>Загвар хариу</summary>

```text
STUDENT ||──o< VISIT >o──|| NURSE
VISIT ||──o< VISITMEDICINE >o──|| MEDICINE

STUDENT       (StudentID [PK], Name, Grade)
NURSE         (NurseID [PK], Name)
VISIT         (VisitID [PK], VisitDate, StudentID [FK], NurseID [FK])
MEDICINE      (MedicineID [PK], MedName)
VISITMEDICINE (VisitID [PK, FK], MedicineID [PK, FK], Dose)
```

- Сурагч тэг эсвэл олон удаа ирнэ; үзлэг яг нэг сурагчийнх. Сувилагч тэг эсвэл олон үзлэг хийнэ; үзлэг яг нэг сувилагчтай.
- VISIT–MEDICINE нь m:m → VISITMEDICINE. `Dose` (тун) тухайн үзлэгт өгсөн эмийн тухай тул холбох хүснэгтэд байна.
- Өөр хувилбар ч зөв байж болно — шугам бүрийн хоёр үзүүр нөхцөлтэй таарч байвал болно.

</details>

<Callout type="warning">
**⚠️ Анхаарах зүйлс**

- **Cardinality = хамгийн ихдээ, modality = хамгийн багадаа.** «Олон» гэдэг нь cardinality, «заавал» гэдэг нь modality.
- **Шугамыг нөгөө үзүүрээс нь унш.** `Customers ||──o< Orders`-ийн `||` нь нэг **захиалгад** хэдэн хэрэглэгч байхыг хэлнэ — нэг хэрэглэгч хэдэн захиалга өгөхийг биш.
- **m:m-ийг хүснэгт болгохоос өмнө задал.** Холбох хүснэгтгүй m:m-ийг шууд хэрэгжүүлэх боломжгүй (A3.1).
- **Сурах бичгийн STUDENT–CLUB жишээ** (х.177) хамаарлыг «one-to-many» гэсэн ч нэг сурагч олон клубт, нэг клубт олон сурагч байдаг тул бодитоор m:m.
- **Тэмдэглэгээ олон** (Chen, UML). Шалгалтад нэгийг тууштай хэрэглэж, эргэлзвэл тэмдгийн тайлбар нэм.

</Callout>

**2.** Фитнес төв гишүүд (MEMBER) ба хичээлүүдийг (CLASS) бүртгэнэ. Гишүүн олон хичээлд бүртгүүлж, нэг хичээлд олон гишүүн ордог. *Construct an ERD that can be implemented in a relational database.* [4]


## A3.2.3 Өгөгдлийн төрлүүд

> 🎯 **Зорилго:** **Outline** the different data types used in relational databases — реляцын өгөгдлийн сангийн өгөгдлийн төрлүүдийг товч тайлбарлах. Энэ хэсгийн төгсгөлд та:
>

> - Төрлийн нийцтэй байдал яагаад чухлыг, буруу төрөл юунд хүргэдгийг тайлбарлана.

### 🤔 Бодоод үзээрэй

Сургуулийн гүйлтийн тэмцээнд оролцогчдын дугаарыг Excel-д текстээр оруулжээ. Дугаараар эрэмбэлэхэд 1, 10, 100, 11, 2… гэж гарч, шүүгчид төөрөв. Яагаад ийм болов?

1. Нас, үнэ, нэр, «дотуур байранд амьдардаг эсэх» — Python-д аль төрлийг ашиглах вэ?
2. Утасны дугаар 88112233. Тоо уу, текст үү? Яагаад?
3. 07/05/2026 гэдэг 5-р сарын 7 үү, 7-р сарын 5 үү?
4. Python-д `"5" + "5"` ба `5 + 5` юу өгөх вэ?

<details>
<summary>Хариу</summary>

1. `int`, `float`, `str`, `bool` (B2.1 модульд).
2. Текст: утсаар тооцоо хийдэггүй, `+976` эсвэл эхний 0 алга болж болохгүй.
3. Мэдэх боломжгүй! Иймээс огноог `YYYY-MM-DD` (2026-05-07) хэлбэрээр хадгалдаг.
4. `"55"` ба `10`. Төрөл нь ямар үйлдэл хийгдэхийг шийддэг — өгөгдлийн санд ч ялгаагүй.

Тэмцээний дугаарыг текстээр хадгалсан тул эхний тэмдэгтээр нь эрэмбэлэгдсэн: «1»-ээр эхэлсэн бүхэн «2»-оос өмнө. Тоо болгож хадгалбал 1, 2, 10, 11, 100 гэж зөв гарна.

</details>

### 📖 Гол ойлголт

Python-д утга бүр төрөлтэй (`int`, `str`…) байдаг шиг өгөгдлийн сангийн талбар бүр **өгөгдлийн төрөл (data type)**-тэй. Төрөл нь ямар утга хадгалах, түүнд ямар үйлдэл хийх, хэрхэн эрэмбэлэхийг шийднэ. IB-ийн жагсаалтад долоон төрөл бий:

| Төрөл | Тайлбар | Жишээ талбар, утга | SQLite-д |
|---|---|---|---|
| CHARACTER(n), CHAR(n) | **Тогтмол урттай** текст: үргэлж n тэмдэгт, дутуу бол ард нь зай нөхнө | `CHAR(8)` UserID: `U0012345` | Текст; уртыг шалгахгүй, зай нөхөхгүй |
| VARCHAR(n) | **Хувьсах урттай** текст: хамгийн ихдээ n тэмдэгт, хэрэгтэй хэрээр зай эзэлнэ | `VARCHAR(50)` Email | Текст; уртыг шалгахгүй |
| INTEGER | Бүхэл тоо | Quantity: `12` | Бүхэл тоо |
| REAL | Бутархай хэсэгтэй тоо | Price: `2.50` | Бутархай тоо |
| DATE | Огноо, `YYYY-MM-DD` | `2026-09-25` | Тусдаа төрөлгүй: `'2026-09-25'` текст |
| TIME | Цаг, `HH:MM:SS` | `08:45:00` | Тусдаа төрөлгүй: текст |
| BOOLEAN | Үнэн/худал утга | IsBoarder: `TRUE` | Тусдаа төрөлгүй: `1` эсвэл `0` |

Нарийн бичиглэл DBMS бүрт өөр: `CHAR` ба `CHARACTER`, `BOOL` ба `BOOLEAN`. Мөнгөнд олон DBMS яг аравтын бутархай хадгалдаг `DECIMAL(10,2)` төрөлтэй; IB-ийн жагсаалтад үүний оронд REAL бий.

**SQLite-ийн онцлог — төрлийн зөвлөмж (type affinity).** SQLite баганын төрлийг хатуу дүрэм биш, зөвлөмж гэж үздэг: `INTEGER` баганад `'ten'` текстийг ч, `CHAR(5)`-д 8 тэмдэгттэй кодыг ч алдаагүй хадгална. Тоо шиг харагдах текстийг (`'95'`, `'0105'`) `INTEGER` баганад тоо болгож хадгална. PostgreSQL зэрэг ихэнх DBMS ба IB-ийн загварт төрөлд таарахгүй оруулалт **алдаа** өгнө.

#### Сонголт яагаад чухал вэ?

- **Индексжүүлэлт үр ашигтай.** Үргэлж 8 тэмдэгттэй UserID-д `CHAR(8)` нь `VARCHAR(8)`-аас үр ашигтай: урт тогтмол тул хувьсах уртыг хадгалах нэмэлт ажил байхгүй. Энэ бол сурах бичгийн хялбаршуулсан тайлбар; орчин үеийн DBMS-д ялгаа ихэвчлэн бага.
- **Боломжит үйлдэл.** Тоо ширхэг, үнийг текстээр хадгалбал тооцоолохоос өмнө хөрвүүлэх хэрэгтэй; эрэмбэлэх, `MAX` тэмдэгт тэмдэгтээр явна.
- **Амжилттай хадгалах.** Утга төрөлдөө таарахгүй бол оруулалт алдаа өгнө (SQLite-ээс бусад ихэнх DBMS-д).
- **Зай.** Нэрэнд `CHAR(30)` өгвөл «Bat» гэх богино нэрийн ард 27 хоосон зай нэмэгдэнэ — нэрэнд `VARCHAR`.

#### Төрлийн нийцтэй байдал

**Төрлийн нийцтэй байдал (data type consistency)** — нэг талбар (attribute) хаана ч (хүснэгт бүрт, өгөгдлийн сан бүрт, апп бүрт) ижил төрөлтэй байх. `StudentID` өгөгдлийн санд INTEGER, аппад текст байвал үйлдэл амжилтгүй болох, буруу мөр шинэчлэгдэх, асуулга буруу үр дүн өгөх эрсдэлтэй. Гадаад түлхүүр ч заасан үндсэн түлхүүртэйгээ ижил төрөлтэй байна.

Жишээ нь `'0105'` (текст) ба `105` (тоо) өөр утга. SQLite-д текст баганад `'0105'` хадгалаад `WHERE ID = 105` гэж тоогоор хайвал **юу ч олдохгүй**, алдаа ч гарахгүй — хамгийн аюултай нь чимээгүй алдаа.

**Ерөнхий дүрэм:** тооцоолох тоо → INTEGER, REAL; таних код, утас, шуудангийн код → текст. Сурах бичгийн STUDENT хүснэгтэд (х.178) `02/01/2010` (өдөр/сар) ба `07/25/2011` (сар/өдөр) хоёр өөр хэлбэр зэрэгцэн орсон байдаг — DATE төрөл ба `YYYY-MM-DD` ийм зөрчлөөс сэргийлнэ.

### 💻 Туршиж үзээрэй

Ижил өгөгдлийг хоёр хүснэгтэд хадгалъя: ItemWrong-д бүгдийг текстээр, ItemRight-д тохирох төрлөөр. `executemany` жагсаалтын tuple бүрийг нэг мөр болгон оруулна; `[row[0] for row in …]` мөр бүрийн эхний талбарыг жагсаалт болгоно; `typeof(Qty)` нь SQLite-ийн функц — утга ямар төрлөөр хадгалагдсаныг хэлнэ.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.executescript("""
CREATE TABLE ItemWrong (Code TEXT,    Qty TEXT,    Price TEXT, Added TEXT);  -- everything as text
CREATE TABLE ItemRight (Code CHAR(5), Qty INTEGER, Price REAL, Added DATE);  -- suitable types
""")
rows = [("A0001", "9", "2.50", "2026-09-01"), ("A0002", "10", "12.00", "2026-10-15"),
        ("A0003", "100", "0.80", "2026-09-20")]
con.executemany("INSERT INTO ItemWrong VALUES (?, ?, ?, ?)", rows)
con.executemany("INSERT INTO ItemRight VALUES (?, ?, ?, ?)",
                [(code, int(qty), float(price), added) for code, qty, price, added in rows])

for table in ["ItemWrong", "ItemRight"]:
    quantities = [row[0] for row in con.execute("SELECT Qty FROM " + table + " ORDER BY Qty")]
    biggest = con.execute("SELECT MAX(Qty) FROM " + table).fetchone()[0]
    print(table, quantities, "MAX:", biggest)

# SQLite only: a wrong type and a too-long code are stored without any error
con.execute("INSERT INTO ItemRight VALUES ('A0004-XL', 'ten', 1.5, '2026-09-30')")
print(con.execute("SELECT Code, Qty, typeof(Qty) FROM ItemRight WHERE Code = 'A0004-XL'").fetchone())
```

Гаралт:

```text
ItemWrong ['10', '100', '9'] MAX: 9
ItemRight [9, 10, 100] MAX: 100
('A0004-XL', 'ten', 'text')
```

- **Текстийг тэмдэгт тэмдэгтээр** харьцуулна: эхний тэмдэгт `'1'` нь `'9'`-өөс бага тул `'10'`, `'100'` нь `'9'`-өөс өмнө орж, `MAX` нь `'9'` болно. Жагсаалтад хашилттай хэвлэгдсэн нь текст гэсэн тэмдэг.
- **INTEGER** баганыг тоогоор эрэмбэлнэ: 9, 10, 100.
- **Сүүлийн мөр:** SQLite `'ten'`-ийг INTEGER баганад текстээр, 8 тэмдэгттэй кодыг `CHAR(5)` баганад бүтнээр нь хадгалсан. PostgreSQL зэрэг DBMS энэ оруулалтыг татгалзана. Төрөл буруу утгыг DBMS татгалздаг эсэхийг SQLite дээр шалгаж болохгүй — SQLite бүгдийг хүлээн авдаг.
- **Өөрөө турш:** `for` давталтад `SELECT SUM(Price) FROM` асуулга нэм. SQLite текстийг тоо руу автоматаар хөрвүүлж хоёр хүснэгтэд ижил 15.3 өгнө — бусад DBMS-д ингэж найдаж болохгүй.

<Callout type="warning">
**⚠️ Анхаарах зүйлс**

- **Утас, код, шуудангийн код — тоо биш, текст.** SQLite-д INTEGER баганад `'+97688112233'` оруулбал `97688112233` болж `+` алга болно; `'0105'` нь `105` болно.
- **Огноог `dd/mm/yyyy` текстээр бүү хадгал.** Текст эрэмбэлэлтээр `'01/12/2025'` (12-р сар) нь `'25/01/2025'`-аас (1-р сар) өмнө гарна. DATE ба `YYYY-MM-DD` ашигла.
- **CHAR(n) ба VARCHAR(n)-ийг бүү андуур:** CHAR үргэлж яг n тэмдэгт, VARCHAR хамгийн ихдээ n.
- **Үнэн/худлыг `'yes'`/`'no'` текстээр биш, BOOLEAN-ээр** хадгал — `'Yes'`, `'YES'`, `'y'` гэх олон хувилбар үүсэхгүй.
- **Төрлийн зөвлөмж (type affinity)** зөвхөн SQLite-ийн онцлог. Шалгалтад «төрөлд таарахгүй утга алдаа өгнө» гэсэн IB-ийн загвараар хариул.

</Callout>

## A3.2.4 Хүснэгт байгуулах ба түлхүүрийн төрлүүд

> 🎯 **Зорилго:** **Construct** tables for relational databases — реляцын өгөгдлийн сангийн хүснэгтүүдийг зохиох. Энэ хэсгийн төгсгөлд та:
>
> - Хүснэгтийг стандарт бичиглэлээр, түлхүүрийг нь тэмдэглэж бичнэ;
> - Үндсэн түлхүүрийг сонгоно: энгийн, нийлмэл эсвэл залгасан;
> - Гадаад түлхүүрээр хүснэгтүүдийг холбоно;
> - Сайн тодорхойлсон хүснэгт өгөгдлийн бүрэн бүтэн байдлыг хэрхэн хамгаалдгийг тайлбарлана.

### 🤔 Бодоод үзээрэй

Улаанбаатараас Дархан явах автобусны тасалбар дээр «Суудал 12» гэж бичжээ. Гэтэл өнөөдөр зургаан автобус явах бөгөөд 12-р суудал бүгдэд нь бий. Тасалбар таны суудлыг давтагдашгүй тодорхойлохын тулд өөр юу заавал бичигдсэн байх ёстой вэ?

1. Сайн үндсэн түлхүүрт тавих хоёр шаардлагыг нэрлэ.
2. Сурагчийн нэр сайн үндсэн түлхүүр мөн үү? Яагаад?
3. `CLUB(StudentID, ClubTitle, TeacherName)` хүснэгтэд нэг сурагч хэд хэдэн клубт явдаг. Аль талбар(ууд) түлхүүр болж чадах вэ?
4. Гадаад түлхүүр байхгүй бичлэгийг заасан бол юу болох вэ?

<details>
<summary>Хариу</summary>

Тасалбарт аялал (огноо, цаг, автобус) ба суудлын дугаар **хамтдаа** бичигдэнэ — энэ бол доор үзэх нийлмэл түлхүүрийн санаа.

1. Давтагддаггүй, хэзээ ч хоосон биш (мөн өөрчлөгддөггүй байх нь зүйтэй).
2. Үгүй — ижил нэртэй хүмүүс байж, нэр солигдож болно.
3. Нэг талбар дангаараа давтагдана; (`StudentID`, `ClubTitle`) хос л давтагдахгүй.
4. Лавлагааны бүрэн бүтэн байдал зөрчигдөнө — DBMS татгалзана (A3.1).

</details>

### 📖 Гол ойлголт

#### Хүснэгтийн бичиглэл

`TABLENAME(PrimaryKey, Field2, Field3, …)` — хүснэгтийн нэр, хаалтанд талбарууд. Энэ модульд түлхүүрийг `[PK]`, `[FK]`, `[PK, FK]` гэж тэмдэглэнэ. Цаасан дээр үндсэн түлхүүрийг доогуур зурж, гадаад түлхүүрийг налуу эсвэл «FK»-ээр тэмдэглэх нь түгээмэл; IB-д нэг тогтсон дүрэм байхгүй тул тайлбар нэмбэл болно.

- Хүснэгт бүр **нэг** биетийн тухай; талбар бүр **нэг** баримт.
- Талбар бүрд өгөгдлийн төрөл, хэмжээ сонгоно (A3.2.3).
- Сайн тодорхойлсон хүснэгт зөв ERD зурахад ба өгөгдлийн бүрэн бүтэн байдлыг хангахад тусална.

Сурах бичгийн сургуулийн жишээ (х.178–179):

```text
STUDENT (StudentID [PK], FirstName, LastName, DateOfBirth, Email)
CLUB    (StudentID [PK, FK], ClubTitle [PK], TeacherName)
TEACHER (TeacherClub [PK], Location)
```

| StudentID | FirstName | LastName | Email |
|---|---|---|---|
| 101 | Fatema | Kada | f.kada@email.com |
| 105 | Alexandru | Buchidau | a.buchidau@email.com |
| 202 | Kada | Hussein | k.hussein@email.com |

| StudentID | ClubTitle | TeacherName |
|---|---|---|
| 105 | Robotics | Bobby Williams |
| 202 | Taekwondo | Dima White |
| 101 | Robotics | Bobby Williams |
| 105 | Arts and Crafts | Jane Doe |

- **STUDENT:** `StudentID` ганцаараа давтагдахгүй — **энгийн үндсэн түлхүүр (simple primary key)**. «Kada» нэг мөрөнд овог, нөгөөд нэр болж давтагдсан — нэр түлхүүр болж чадахгүй.
- **CLUB:** талбар бүр давтагдана (105 хоёр удаа, Robotics хоёр удаа). Хоёр зам бий: (`StudentID`, `ClubTitle`) нийлмэл түлхүүр, эсвэл мөр бүрд шинэ дугаар талбар (сурах бичигт `ClubID`) нэмэх. Зөвхөн мөрийг ялгах зорилгоор нэмсэн, бодит утгагүй ийм дугаарыг **зохиомол түлхүүр (surrogate key)** гэнэ.
- CLUB-ийн `StudentID` нь STUDENT рүү заасан **гадаад түлхүүр**.
- «Bobby Williams» хоёр мөрөнд давтагдсан — үүнийг A3.2.5-д нормчлолоор шийднэ.

#### Нийлмэл ба залгасан түлхүүр

| | Нийлмэл түлхүүр (composite key) | Залгасан түлхүүр (concatenated key) |
|---|---|---|
| Бүтэц | Хоёр ба түүнээс олон **тусдаа** талбар хамтдаа давтагдахгүй | Хэд хэдэн талбарын утгыг **нэг** талбарт залгасан |
| Жишээ | CLUB: (`StudentID`, `ClubTitle`) | TEACHER: `TeacherClub` = «Bobby Williams Robotics» |
| Давуу тал | Хэсэг бүр өөрөө гадаад түлхүүр байж болно | Нэг талбарт түлхүүр шаардлагатай үед; уншихад амар |
| Сул тал | Түүнийг заахад гадаад түлхүүр хоёр талбартай болно | Хайх, шинэчлэхэд хэцүү: багш нэрээ, клуб гарчгаа солиход түлхүүр өөрчлөгдөнө |

Залгахдаа тусгаарлагч хэрэглэ. «1-р байрны 12 тоот» ба «11-р байрны 2 тоот» хоёулаа тусгаарлагчгүй бол `112` болж давхцана; `1-12`, `11-2` гэвэл ялгарна. Хоёр түлхүүрийн сул тал ба тусгаарлагчийн жишээ сурах бичигт байхгүй нэмэлт.

#### Гадаад түлхүүр ба бүрэн бүтэн байдал

- Гадаад түлхүүрийн утга бүр холбогдох хүснэгтийн **байгаа** үндсэн түлхүүртэй таарна (лавлагааны бүрэн бүтэн байдал, A3.1), төрөл нь ч ижил (A3.2.3).
- DBMS байхгүй бичлэгийг заасан мөрийг татгалзаж, заагдсан хэвээр байгаа бичлэгийг устгахыг хориглоно.
- `NOT NULL`, `UNIQUE`, `CHECK` хязгаарлалтаар хүснэгт өөрийн өгөгдлийг хамгаална.

### 💻 Туршиж үзээрэй

Доорх `school_tables.py` нь сурах бичгийн гурван хүснэгтийг гурван төрлийн түлхүүртэй үүсгээд, буруу оруулалт хийж үзнэ.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("PRAGMA foreign_keys = ON")
con.executescript("""
CREATE TABLE STUDENT (
    StudentID INTEGER PRIMARY KEY,                     -- simple primary key
    FirstName VARCHAR(30) NOT NULL,
    LastName  VARCHAR(30) NOT NULL);
CREATE TABLE TEACHER (
    TeacherClub VARCHAR(60) PRIMARY KEY,               -- concatenated key: name + club in ONE field
    Location    CHAR(4));
CREATE TABLE CLUB (
    StudentID   INTEGER REFERENCES STUDENT(StudentID), -- foreign key
    ClubTitle   VARCHAR(30),
    TeacherName VARCHAR(30),
    PRIMARY KEY (StudentID, ClubTitle));               -- composite key: two fields together
INSERT INTO STUDENT VALUES (101, 'Fatema', 'Kada'), (105, 'Alexandru', 'Buchidau'), (202, 'Kada', 'Hussein');
INSERT INTO TEACHER VALUES ('Jane Doe Arts and Crafts', 'L101'), ('Bobby Williams Robotics', 'H203'),
                           ('Dima White Taekwondo', 'B353');
INSERT INTO CLUB VALUES (105, 'Robotics', 'Bobby Williams'), (202, 'Taekwondo', 'Dima White'),
                        (101, 'Robotics', 'Bobby Williams'), (105, 'Arts and Crafts', 'Jane Doe');
""")
attempts = [("105 joins Robotics again", "INSERT INTO CLUB VALUES (105, 'Robotics', 'Bobby Williams')"),
            ("202 joins Robotics", "INSERT INTO CLUB VALUES (202, 'Robotics', 'Bobby Williams')"),
            ("Unknown student 999", "INSERT INTO CLUB VALUES (999, 'Chess', 'Dima White')"),
            ("Bobby Williams Robotics again", "INSERT INTO TEACHER VALUES ('Bobby Williams Robotics', 'H204')")]
for label, sql in attempts:
    try:
        con.execute(sql)
        print(label, "-> accepted")
    except sqlite3.IntegrityError as error:
        print(label, "-> rejected:", error)
count = con.execute("SELECT COUNT(*) FROM CLUB WHERE TeacherName = 'Bobby Williams'").fetchone()[0]
print(count, "rows repeat 'Bobby Williams'")
```

Гаралт (эхлээд өөрөө таамагла):

```text
105 joins Robotics again -> rejected: UNIQUE constraint failed: CLUB.StudentID, CLUB.ClubTitle
202 joins Robotics -> accepted
Unknown student 999 -> rejected: FOREIGN KEY constraint failed
Bobby Williams Robotics again -> rejected: UNIQUE constraint failed: TEACHER.TeacherClub
3 rows repeat 'Bobby Williams'
```

- Нийлмэл түлхүүр зөвхөн **хосын** давхардлыг татгалзана: 105 өөр клубт, 202 Robotics-т ороход болно.
- Гадаад түлхүүр 999 гэх байхгүй сурагчийг зогсоов. Залгасан түлхүүр нэг багш–клубын хосыг хоёр дахь удаа оруулахгүй.
- `COUNT(*)` нөхцөлд таарсан мөрийн тоог олно: «Bobby Williams» одоо гурван мөрөнд — дараагийн хэсгийн асуудал.

<Callout type="warning">
**⚠️ Анхаарах зүйлс**

- **Нийлмэл ≠ залгасан.** Нийлмэл — хэд хэдэн **тусдаа** талбар; залгасан — утгуудыг **нэг** талбарт нийлүүлсэн.
- **Нэр томьёоны зөрүү.** Зарим эх сурвалж «concatenated key»-г composite key-ийн өөр нэр гэж хэрэглэдэг. IB-ийн сурах бичиг хоёрыг ялгадаг тул энэ хичээлд ч ялгана.
- **Залгасан түлхүүрт тусгаарлагч хэрэглэ**, утга нь өөрчлөгдөж болохыг санаж бай.
- **Нэр, имэйлийг үндсэн түлхүүр болгохоос зайлсхий:** давтагдаж, өөрчлөгдөж болно. Эргэлзвэл зохиомол түлхүүр нэм.
- **Гадаад түлхүүр заасан үндсэн түлхүүртэйгээ ижил төрөлтэй** байна (A3.2.3).

</Callout>

| Монгол | English | Тайлбар |
|---|---|---|
| Энгийн үндсэн түлхүүр | Simple primary key | Ганц талбараас бүрдсэн үндсэн түлхүүр |

## A3.2.5 Нормаль хэлбэрүүд: 1NF, 2NF, 3NF

> 🎯 **Зорилго:** **Explain** the difference between normal forms — нормаль хэлбэрүүдийн ялгааг шалтгаантай нь тайлбарлах. Энэ хэсгийн төгсгөлд та:
>

### 📖 Гол ойлголт

**Нормчлол (normalisation)** бол реляцын өгөгдлийн сангийн өгөгдлийг илүүдлийг (A3.1) багасгаж, бүрэн бүтэн байдлыг сайжруулахаар хүснэгтүүдэд зохион байгуулах үйл явц.

- Баримт бүр **нэг л** газар хадгалагдана → шинэчлэлийн гажиг цөөрч, зай хэмнэгдэнэ.
- Хүснэгт жижиг, мөр бүрт өгөгдөл бага → диск ба санах ойн хоорондох оролт/гаралтын (I/O) дамжуулалт цөөн.
- Шат дараатай: **нормаль хэлбэр (normal form, NF)** бүр өмнөхийнхөө бүх дүрэм дээр нэг шинэ дүрэм нэмнэ: 1NF → 2NF → 3NF. Нормчлоогүй хүснэгтийг **UNF** (unnormalised form) гэнэ.

| Гажиг (anomaly) | Юу болох вэ | Клубын хүснэгтэд |
|---|---|---|
| Шинэчлэлийн гажиг (update anomaly) | Нэг баримт олон мөрөнд; заримыг нь л засвал зөрчилдөнө | Bold-ийн утас гурван мөрөнд |
| Оруулалтын гажиг (insert anomaly) | Өөр өгөгдөлгүйгээр баримт оруулж чадахгүй | Гишүүнгүй клуб |
| Устгалын гажиг (delete anomaly) | Мөр устгахад хэрэгтэй өөр баримт хамт алга болно | Saraa-гийн мөрийг устгахад Taekwondo, Tuya-гийн утас алга |

Сурах бичигт зөвхөн «update anomalies» гэж бий; бусад хоёр нэр нь түгээмэл хэрэглэгддэг нэмэлт нэр томьёо.

#### 1NF: түлхүүр, давтагдах бүлэггүй, атомар утга

| Дүрэм | Утга | Клубын хүснэгтэд |
|---|---|---|
| Үндсэн түлхүүртэй | Мөр бүр нэг талбар эсвэл нийлмэл түлхүүрээр ялгагдана | 105 хоёр мөрөнд — түлхүүр алга |
| Давтагдах бүлэггүй (no repeating groups) | Club1, Club2, Club3 гэх мэт ижил мэдээллийг давтсан багана байхгүй | Клуб бүрд багана нэмбэл ийм болно |
| Атомар утга (atomic values) | Нүд бүрт цааш задрахгүй **ганц** утга: жагсаалт, хэсэгтэй утга байхгүй | «Robotics, Chess»; Name-ийг FirstName, LastName болгож задлах |

1NF болгосны дараа: нэг мөрөнд нэг клуб, нэр задарсан, үндсэн түлхүүр (`StudentID`, `ClubTitle`):

| StudentID [PK] | ClubTitle [PK] | FirstName | LastName | TeacherName | TeacherPhone |
|---|---|---|---|---|---|
| 101 | Robotics | Anu | Dorj | Bold | 99110001 |
| 101 | Chess | Anu | Dorj | Bold | 99110001 |
| 105 | Robotics | Bat | Tsend | Bold | 99110001 |
| 105 | Chess | Bat | Tsend | Bold | 99110001 |
| 202 | Taekwondo | Saraa | Od | Tuya | 88002233 |

Хүснэгт 1NF-д орсон ч илүүдэл бүр нэмэгдэв: Bold-ийн утас одоо дөрвөн удаа. Цааш явахын тулд талбарууд бие биенээ хэрхэн тодорхойлдгийг харах хэрэгтэй.

#### Функциональ хамаарал (functional dependency)

**Функциональ хамаарал** `A → B` («A нь B-г тодорхойлно» гэж уншина) гэдэг нь «A-ийн утгыг мэдвэл B-ийн утга **яг нэг** байна» гэсэн үг; A-г **тодорхойлогч (determinant)** гэнэ.

- `StudentID → FirstName`: 105 гэвэл үргэлж Bat.
- `FirstName → StudentID` **биш**: хоёр өөр сурагч Bat нэртэй байж болно. Сумны чиглэл чухал.
- Энэ нь A3.1-ийн хүснэгт хоорондын **хамаарал (relationship)** биш — нэг хүснэгтийн **талбаруудын** хоорондох холбоо.

| Төрөл | Түлхүүр биш талбар юунаас хамаарна | Жишээ (түлхүүр = `StudentID`, `ClubTitle`) |
|---|---|---|
| Бүрэн функциональ хамаарал (full functional dependency) | **Бүтэн** түлхүүрээс | Хэрэв клубт элссэн огноо `JoinDate` байсан бол: (`StudentID`, `ClubTitle`) → `JoinDate` |
| Хэсэгчилсэн хамаарал (partial dependency) | Нийлмэл түлхүүрийн зөвхөн **хэсгээс** | `StudentID → FirstName`; `ClubTitle → TeacherName` |
| Дамжсан хамаарал (transitive dependency) | Түлхүүр **биш** өөр талбараас | `TeacherName → TeacherPhone` — TeacherName түлхүүр биш (2NF-ийн дараах CLUB-д `ClubTitle → TeacherName → TeacherPhone`) |

#### 2NF ба 3NF

| Хэлбэр | Дүрэм | Клубын хүснэгтэд | Засвар |
|---|---|---|---|
| 2NF | 1NF + хэсэгчилсэн хамааралгүй: түлхүүр биш талбар бүр **бүтэн** түлхүүрээс хамаарна | `FirstName`, `LastName` нь зөвхөн `StudentID`-аас; `TeacherName`, `TeacherPhone` нь зөвхөн `ClubTitle`-аас | `STUDENT(StudentID [PK], FirstName, LastName)`, `CLUB(ClubTitle [PK], TeacherName, TeacherPhone)`, `MEMBERSHIP(StudentID [PK, FK], ClubTitle [PK, FK])` |
| 3NF | 2NF + дамжсан хамааралгүй: түлхүүр биш талбар өөр түлхүүр биш талбараас хамаарахгүй | CLUB-д `ClubTitle → TeacherName → TeacherPhone` | `TEACHER(TeacherID [PK], TeacherName, TeacherPhone)`, `CLUB(ClubTitle [PK], TeacherID [FK])` |

Нэр муу түлхүүр тул (A3.1) TEACHER-т `TeacherID` нэмэв. Одоо Bold-ийн утас TEACHER-т ганц удаа; гишүүнгүй клуб CLUB-д бичигдэнэ; Saraa гарахад MEMBERSHIP-ийн ганц мөр л устна. Уламжлалт хэллэгээр (сурах бичигт байхгүй): түлхүүр биш талбар бүр «**the key** (1NF), **the whole key** (2NF), **and nothing but the key** (3NF)»-ээс хамаарна.

Цааш нь **олон утгат хамаарал (multi-valued dependency)** бий: нэг талбар бие биеэсээ үл хамаарах хоёр жагсаалтыг тодорхойлно (машины загвар → өнгөнүүд, загвар → үйлдвэрлэсэн онууд). Үүнийг 4NF шийддэг. IB-ийн шалгалтад 3NF хүртэл; энэ нэр томьёог л мэд.

IB Guide нормчлолоор шийдэх асуудлуудыг англиар ингэж нэрлэдэг: *data duplication* (илүүдэл), *missing data* (гажгаас болж оруулж чадахгүй эсвэл алга болох өгөгдөл), *data dependencies* (функциональ хамаарал), *composite key dependencies* (хэсэгчилсэн хамаарал), *transitive dependencies* (дамжсан хамаарал), *multi-valued dependencies* (олон утгат хамаарал).

### 💻 Туршиж үзээрэй

Функциональ хамаарлыг өгөгдөл дээр шалгаж болно: хоёр мөрийн A ижил атал B өөр бол `A → B` биш. `columns.index(a)` нь баганын нэрээр түүний дугаарыг олно.

```python
columns = ["StudentID", "ClubTitle", "FirstName", "TeacherName", "TeacherPhone"]
rows = [(101, "Robotics", "Anu", "Bold", "99110001"),
        (101, "Chess", "Anu", "Bold", "99110001"),
        (105, "Robotics", "Bat", "Bold", "99110001"),
        (105, "Chess", "Bat", "Bold", "99110001"),
        (202, "Taekwondo", "Saraa", "Tuya", "88002233")]

def determines(a, b):
    """False as soon as two rows agree on column a but differ on column b."""
    i = columns.index(a)
    j = columns.index(b)
    for row1 in rows:
        for row2 in rows:
            if row1[i] == row2[i] and row1[j] != row2[j]:
                return False
    return True

for a, b in [("StudentID", "FirstName"), ("ClubTitle", "TeacherName"), ("TeacherName", "TeacherPhone"),
             ("TeacherName", "ClubTitle"), ("StudentID", "ClubTitle")]:
    print(a, "->", b, determines(a, b))
```

Гаралт:

```text
StudentID -> FirstName True
ClubTitle -> TeacherName True
TeacherName -> TeacherPhone True
TeacherName -> ClubTitle False
StudentID -> ClubTitle False
```

Bold хоёр клубтэй тул `TeacherName → ClubTitle` биш. **Хялбаршуулсан арга:** өгөгдөл функциональ хамаарлыг зөвхөн **үгүйсгэж** чадна (нэг жишээ хангалттай), харин **баталж** чадахгүй — таван мөр таарсан ч дараагийн мөр эвдэж болно. Бодит өгөгдлийн санд функциональ хамаарлыг өгөгдлийн утга, байгууллагын дүрмээс тогтооно.

<Callout type="warning">
**⚠️ Анхаарах зүйлс**

- **«Хамаарал» хоёр утгатай.** Хүснэгт хоорондын хамаарал (relationship: 1:m, m:m) ба талбар хоорондын функциональ хамаарал (functional dependency). Хоёр дахийг үргэлж «функциональ», «хэсэгчилсэн», «дамжсан» гэсэн тодотголтой бич.
- **2NF-ийн асуудал зөвхөн нийлмэл түлхүүртэй хүснэгтэд гарна.** Ганц талбартай үндсэн түлхүүртэй 1NF хүснэгт автоматаар 2NF — гэхдээ 3NF гэсэн үг **биш**.
- **Хэсэгчилсэн ≠ дамжсан.** Хэсэгчилсэн — түлхүүрийн **хэсгээс**; дамжсан — түлхүүр **биш** талбараас.
- **Давтагдсан утга бүхэн 1NF-ийн зөрчил биш.** Гадаад түлхүүрийн утга (MEMBERSHIP-ийн `StudentID`) давтагдах нь зөв (A3.1).
- **Сурах бичгийн 3NF жишээнд** (х.181) CLUB хүснэгтэд ClubID 105 хоёр удаа орсон — үндсэн түлхүүр давтагдсан алдаа.

</Callout>

## A3.2.6 3NF хүртэл нормчлох

> 🎯 **Зорилго:** **Construct** a database normalised to 3NF for a range of real-world scenarios — бодит нөхцөлүүдэд 3NF хүртэл нормчилсон өгөгдлийн сан зохиох. Энэ хэсгийн төгсгөлд та:
>
> - Нормчлоогүй хүснэгтэд 1NF, 2NF, 3NF-ийг дарааллаар нь хэрэглэнэ;
> - Эцсийн хүснэгтүүдийг үндсэн ба гадаад түлхүүртэй нь зохионо;
> - Нормчлол шинэчлэлийн гажгийг арилгадгийг харуулна.

### 🤔 Бодоод үзээрэй

Сургуулийн номын санч ном бүрийг Excel-ийн нэг мөрөнд бичдэг: зохиолч, гарчиг, хуудас, хянан засварлагчид. Нэг зохиолчийн овог буруу бичигдсэнийг олж засахдаа тэр зохиолчийн хоёр номын нэгийг нь л засчихжээ.

1. 1NF-ийн гурван дүрмийг хэл.
2. 2NF ямар нэмэлт дүрэм нэмдэг вэ? 3NF?
3. 2NF-ийн асуудал ганц талбартай түлхүүрт үү, нийлмэл түлхүүрт үү гарах вэ?

<details>
<summary>Хариу</summary>

1. Үндсэн түлхүүртэй; давтагдах бүлэггүй; бүх утга атомар.
2. 2NF: хэсэгчилсэн хамааралгүй. 3NF: дамжсан хамааралгүй.
3. Зөвхөн нийлмэл түлхүүрт — түлхүүр ганц талбартай бол «хэсэг» гэж байхгүй.

Номын санчийн асуудал бол шинэчлэлийн гажиг: зохиолчийн нэр олон мөрөнд хадгалагдсан.

</details>

### 📖 Гол ойлголт

#### Алхам алхмаар

1. **UNF → 1NF.** Үндсэн түлхүүр сонго; жагсаалт, давтагдах бүлгийг тусдаа мөр болгон задал; утга бүрийг атомар болго. Түлхүүр нийлмэл болж магадгүй.
2. **1NF → 2NF** (зөвхөн нийлмэл түлхүүртэй бол). Түлхүүр биш талбар бүрээс «түлхүүрийн аль хэсэг намайг тодорхойлдог вэ?» гэж асуу. Хэсгээс хамаарсныг тэр хэсгийг түлхүүр болгосон шинэ хүснэгтэд гарга.
3. **2NF → 3NF.** «Түлхүүр биш өөр талбар намайг тодорхойлдог уу?» Тийм бол тэр талбарыг түлхүүр болгосон шинэ хүснэгтэд гаргаж, хуучин хүснэгтэд гадаад түлхүүр болгон үлдээ.
4. **Шалга.** Хүснэгт бүрийн `[PK]`, `[FK]`-г тэмдэглэ; m:m бүр холбох хүснэгттэй; алхам бүрт ямар функциональ хамаарлыг арилгаснаа нэрлэ.

#### Жишээ: BOOKS хүснэгт

Сурах бичгийн хүснэгтэд (х.181) ном бүр нэг хянан засварлагчтай. Бид 2-р номд хоёр **хянан засварлагч (proofreader)** өгснөөр гурван алхам бүгд харагдана.

| BookID | AuthorID | Author | Title | Pages | ProofReaders |
|---|---|---|---|---|---|
| 1 | 101 | Boris Brown | History of AI | 353 | Amanda |
| 2 | 102 | Chris Joe | The Great G | 200 | Hamilton, Juan |
| 3 | 19 | Danny Bill | Big Tonny | 190 | Juan |
| 5 | 101 | Boris Brown | Amazing Future | 399 | Amanda |

**1NF.** `Author`-ийг `AuthorFirstName`, `AuthorLastName` болгож задална; «Hamilton, Juan»-ийг хоёр мөр болгоно. 2-р ном хоёр мөрөнд гарч `BookID` давтагдах тул түлхүүр нь (`BookID`, `ProofReader`) нийлмэл болно — 5 мөр. Энэ хүснэгт ба түүний функциональ хамаарлууд:

```text
BOOKS_1NF (BookID [PK], ProofReader [PK], AuthorID, AuthorFirstName, AuthorLastName, Title, Pages)
```

- `BookID → AuthorID, Title, Pages` — түлхүүрийн **хэсгээс**: хэсэгчилсэн хамаарал.
- `AuthorID → AuthorFirstName, AuthorLastName` — түлхүүр биш талбараас: дамжсан хамаарал.
- Бүтэн түлхүүрээс (`BookID`, `ProofReader`) хамаарах өөр талбар алга.

**2NF.** `BookID`-аас хамаарах бүхнийг гаргана:

```text
BOOKS              (BookID [PK], AuthorID, AuthorFirstName, AuthorLastName, Title, Pages)
BOOKS_PROOFREADERS (BookID [PK, FK], ProofReader [PK])
```

**3NF.** BOOKS-д `BookID → AuthorID → AuthorFirstName` дамжсан хамаарал үлдсэн тул AUTHOR хүснэгт гаргана. Мөн хянан засварлагчийн нэр түлхүүрийн хэсэг болсон; нэр муу түлхүүр (A3.1) бөгөөд хянан засварлагч өөрийн мэдээлэлтэй (утас, имэйл) тусдаа биет тул `ProofReaderID` өгнө. Энэ сүүлийн алхмыг 3NF-ийн дүрэм шаарддаггүй — сайн дизайны шийдвэр:

```text
AUTHOR             (AuthorID [PK], AuthorFirstName, AuthorLastName)
BOOKS              (BookID [PK], AuthorID [FK], Title, Pages)
PROOFREADERS       (ProofReaderID [PK], ProofReader)
BOOKS_PROOFREADERS (BookID [PK, FK], ProofReaderID [PK, FK])
```

Дөрвөн хүснэгт бүр **нэг** зүйлийн тухай. Ном–хянан засварлагч нь m:m (нэг ном олон, нэг хүн олон ном) тул BOOKS_PROOFREADERS холбох хүснэгт.

### 💻 Туршиж үзээрэй

`normalise_books.py` эхлээд 1NF хүснэгтэд зохиолчийн овгийг **нэг** мөрөнд засаж гажиг үүсгэнэ. Дараа нь 3NF хүснэгтүүдэд нэг `UPDATE` хийнэ. `UPDATE … SET … WHERE` нь нөхцөлд таарсан мөрийн утгыг өөрчилнө.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("PRAGMA foreign_keys = ON")
con.executescript("""
CREATE TABLE BOOKS_1NF (BookID INTEGER, ProofReader TEXT, AuthorID INTEGER, AuthorFirstName TEXT,
                        AuthorLastName TEXT, Title TEXT, Pages INTEGER, PRIMARY KEY (BookID, ProofReader));
INSERT INTO BOOKS_1NF VALUES (1, 'Amanda', 101, 'Boris', 'Brown', 'History of AI', 353),
    (2, 'Hamilton', 102, 'Chris', 'Joe', 'The Great G', 200), (2, 'Juan', 102, 'Chris', 'Joe', 'The Great G', 200),
    (3, 'Juan', 19, 'Danny', 'Bill', 'Big Tonny', 190), (5, 'Amanda', 101, 'Boris', 'Brown', 'Amazing Future', 399);
CREATE TABLE AUTHOR (AuthorID INTEGER PRIMARY KEY, AuthorFirstName TEXT, AuthorLastName TEXT);
CREATE TABLE BOOKS (BookID INTEGER PRIMARY KEY, AuthorID INTEGER REFERENCES AUTHOR(AuthorID),
                    Title TEXT, Pages INTEGER);
CREATE TABLE PROOFREADERS (ProofReaderID INTEGER PRIMARY KEY, ProofReader TEXT);
CREATE TABLE BOOKS_PROOFREADERS (BookID INTEGER REFERENCES BOOKS(BookID),
                                 ProofReaderID INTEGER REFERENCES PROOFREADERS(ProofReaderID),
                                 PRIMARY KEY (BookID, ProofReaderID));
INSERT INTO AUTHOR VALUES (101, 'Boris', 'Brown'), (102, 'Chris', 'Joe'), (19, 'Danny', 'Bill');
INSERT INTO BOOKS VALUES (1, 101, 'History of AI', 353), (2, 102, 'The Great G', 200),
                         (3, 19, 'Big Tonny', 190), (5, 101, 'Amazing Future', 399);
INSERT INTO PROOFREADERS VALUES (100, 'Amanda'), (222, 'Hamilton'), (123, 'Juan');
INSERT INTO BOOKS_PROOFREADERS VALUES (1, 100), (2, 222), (2, 123), (3, 123), (5, 100);
""")
con.execute("UPDATE BOOKS_1NF SET AuthorLastName = 'Braun' WHERE BookID = 1")      # one row only
print("1NF:", con.execute("""SELECT BookID, AuthorLastName FROM BOOKS_1NF
                             WHERE AuthorID = 101 ORDER BY BookID""").fetchall())

con.execute("UPDATE AUTHOR SET AuthorLastName = 'Braun' WHERE AuthorID = 101")     # one row is enough
rows = con.execute("""SELECT BOOKS.BookID, AUTHOR.AuthorLastName, PROOFREADERS.ProofReader
                      FROM BOOKS JOIN AUTHOR ON BOOKS.AuthorID = AUTHOR.AuthorID
                      JOIN BOOKS_PROOFREADERS ON BOOKS.BookID = BOOKS_PROOFREADERS.BookID
                      JOIN PROOFREADERS ON BOOKS_PROOFREADERS.ProofReaderID = PROOFREADERS.ProofReaderID
                      ORDER BY BOOKS.BookID, PROOFREADERS.ProofReader""").fetchall()
for row in rows:
    print(row)
```

Гаралт:

```text
1NF: [(1, 'Braun'), (5, 'Brown')]
(1, 'Braun', 'Amanda')
(2, 'Joe', 'Hamilton')
(2, 'Joe', 'Juan')
(3, 'Bill', 'Juan')
(5, 'Braun', 'Amanda')
```

1NF хүснэгтэд 101-р зохиолч хоёр өөр овогтой болов — шинэчлэлийн гажиг. 3NF-д нэг мөр засахад түүний бүх ном шинэ овогтой. 2-р номд гурав дахь хянан засварлагч нэмэхэд BOOKS_PROOFREADERS-т `(2, 100)` гэх нэг мөр л нэмнэ — давтагдах бүлэг үүсэхгүй.

<Callout type="warning">
**⚠️ Анхаарах зүйлс**

- **Алхмуудыг дарааллаар нь бич.** Шалгалтад шууд эцсийн хүснэгтүүдийг бичвэл «showing each step» гэсэн оноо алдана. Алхам бүрт ямар функциональ хамаарлыг (`BookID → Title` хэсэгчилсэн гэх мэт) арилгаснаа нэрлэ.
- **Гаргасан талбарын тодорхойлогчийг хуучин хүснэгтэд гадаад түлхүүр болгон үлдээ** (`BOOKS.AuthorID`) — эс тэгвэл хүснэгтүүд холбогдохгүй.
- **Сурах бичгийн ялгаа.** Сурах бичгийн BOOKS ганц `BookID` түлхүүртэй тул 1NF хүснэгт нь аль хэдийн 2NF; зохиолчийн нэрийг салгах нь энэ хичээлийн тодорхойлолтоор 3NF-ийн алхам (дамжсан хамаарал), харин сурах бичиг үүнийг 2NF гэж бичсэн.
- **Сурах бичгийн хэвлэлийн алдаа** (х.182): «non-transitive dependencies» нь «transitive» байх ёстой; 2NF хүснэгтэд «Big Tonny 180» гэсэн нь 190. Хянан засварлагчийг тусад нь гаргах шалтгаан нь дамжсан хамаарал биш, m:m хамаарал.

</Callout>

| Монгол | English | Тайлбар |

**1.** `MARK(StudentID, StudentName, SubjectCode, SubjectName, Mark)` хүснэгтийн түлхүүр нь (`StudentID`, `SubjectCode`) нийлмэл түлхүүр.

- a) *Explain why the table is not in second normal form.* [2]
- b) *Construct a set of tables in 3NF, identifying all primary and foreign keys.* [4]

<details>
<summary>Хариу</summary>

a) `StudentName` зөвхөн `StudentID`-аас, `SubjectName` зөвхөн `SubjectCode`-оос хамаарна — тус бүр нийлмэл түлхүүрийн хэсэг [1]. Эдгээр хэсэгчилсэн хамаарал 2NF-ийг зөрчинө: 2NF түлхүүр биш талбар бүр бүтэн түлхүүрээс хамаарахыг шаарддаг [1].

b) `STUDENT(StudentID [PK], StudentName)` [1]; `SUBJECT(SubjectCode [PK], SubjectName)` [1]; `MARK(StudentID, SubjectCode, Mark)`, үндсэн түлхүүр (`StudentID`, `SubjectCode`) [1]; MARK-ийн `StudentID`, `SubjectCode` нь STUDENT ба SUBJECT рүү заасан гадаад түлхүүр [1].

**2.** Агуулахын хүснэгт `STOCK(ProductCode, Warehouse, ProductName, SupplierID, SupplierName, WarehouseCity, Qty)`. Нэг бараа хэд хэдэн агуулахад хадгалагдах тул түлхүүр нь (`ProductCode`, `Warehouse`); `Qty` нь тухайн агуулах дахь тухайн барааны тоо. Бараа бүр нэг нэртэй, нэг нийлүүлэгчээс ирдэг; нийлүүлэгч бүр нэг нэртэй, агуулах бүр нэг хотод байрладаг. 3NF хүртэл нормчил.

<summary>Хариу</summary>

## A3.2.7 Денормчлолын хэрэгцээг үнэлэх

> 🎯 **Зорилго:** **Evaluate** the need for denormalising databases — давуу ба сул талыг жинлэж, тухайн системийг денормчлох эсэхэд үндэслэлтэй дүгнэлт гаргах. Энэ хэсгийн төгсгөлд та:
>
> - Нормчлол ба денормчлолын давуу, сул талыг тоочно;
> - Денормчлол гүйцэтгэлийг сайжруулах нөхцөлийг танина;
> - Өгөгдсөн системийг денормчлох эсэхийг үнэлнэ.

### 🤔 Бодоод үзээрэй

Цагаан сарын өмнө онлайн дэлгүүрийн бүтээгдэхүүний хуудсыг минутад мянга мянган хүн үздэг. Харин үнэ, тайлбарыг долоо хоногт хэдхэн удаа өөрчилдөг. Хуудас бүрийг харуулахын тулд таван хүснэгтийг JOIN-оор холбох нь зөв үү?

1. Банк секундэд 10 000 гүйлгээ бүртгэдэг. Голдуу уншдаг уу, бичдэг үү?
2. Сургуулийн улирлын дүнгийн тайлан улиралд нэг удаа гардаг. Голдуу уншдаг уу, бичдэг үү?
3. Алинд нь гажгаас сэргийлэх нь илүү чухал вэ? Яагаад?
4. 5 JOIN-тэй асуулга яагаад удаан байж болох вэ?

<details>
<summary>Хариу</summary>

1. Бичилт их — нормчилсон байх ёстой.
2. Уншилт их — илүүдэлтэй хуулбар тус болж магадгүй.
3. Банк: бичилт олон тул гажиг гарах боломж олон, мөнгөний алдаа үнэтэй.
4. JOIN бүр хоёр хүснэгтийн мөрүүдийг тааруулах ажил нэмнэ.

Онлайн дэлгүүрийн бүтээгдэхүүний хуудас ч уншилт давамгайлсан — доор үзэх денормчлолын сонгодог тохиолдол.

### 📖 Гол ойлголт

#### Нормчлолын давуу ба сул тал

| Давуу тал | Учир | Сул тал | Учир |
|---|---|---|---|
| Илүүдэл бага | Зай хэмнэж, өгөгдлийг нийцтэй байлгана | Схем төвөгтэй | Олон хүснэгт — ойлгоход хэцүү |
| Бүрэн бүтэн байдал | Хамаарал ба функциональ хамаарлын дүрэм | Асуулга төвөгтэй | Олон JOIN гүйцэтгэлийг бууруулж болно |
| Өгөгдөл үр ашигтай авах | Хамаарал тодорхой | Илүү зай (сурах бичгийн мэдэгдэл) | Олон хүснэгт, хамаарал |
| Өргөтгөх боломж | Бүтцийг өөрчлөхгүйгээр өгөгдөл нэмнэ | Бүх өгөгдөлд тохирохгүй | Зөвхөн реляцын зарчимд суурилсан |
| Нийцтэй байдал | Давхардалгүй, тодорхой хамаарал | Тэнцвэр олоход хэцүү | Хэт их эсвэл хэт бага нормчлох |
| Засвар хялбар | Баримтыг нэг л газар өөрчилнө | Шинэчлэлийн нэмэлт ачаалал | Нэг үйлдэл хэд хэдэн хүснэгтэд хүрч болно |

«Илүүдэл бага → зай хэмнэнэ» ба «илүү зай» зөрчилдөх мэт санагдана. Ихэнхдээ нормчлол зай хэмнэдэг; олон хүснэгт, түлхүүр, индекс нэмэгдэхэд л нэмэлт зардал гарна.

#### Денормчлол: санаатай илүүдэл

**Денормчлол (denormalisation)** — асуулгын гүйцэтгэлийг сайжруулахын тулд дизайнд илүүдлийг **санаатайгаар** зөвшөөрөх. Нормчлоогүй «муу» дизайнаас ялгаатай нь эхлээд нормчилж, дараа нь шалтгаантайгаар хуулбар нэмдэг.

| Давуу тал | Сул тал |
|---|---|
| Асуулга хурдан: уншилт ихтэй асуулгад JOIN цөөн | Илүүдэл: шинэчлэлтийг зөв удирдахгүй бол хуулбарууд зөрчилдөнө |
| Өгөгдөл авахад хялбар: апп уншдаг хэлбэрээр нь хадгална | Нэмэлт зай: илүүдэл хуулбар зай эзэлнэ |
| Өргөтгөхөд хялбар: төвөгтэй хамаарлын ачаалал бага | Засвар хүнд: бүрэн бүтэн байдлыг хадгалах нарийн төлөвлөлт хэрэгтэй |

Денормчлол ихэвчлэн тус болдог газар:

- **Уншилт давамгайлсан (read-intensive) апп** — голдуу уншиж, ховор шинэчилдэг (бүтээгдэхүүний каталог).
- **Тайлан, шинжилгээ** — их өгөгдөл дээрх төвөгтэй тайлан энгийн бүтцээр хурдан гарна.
- **Өгөгдлийн агуулах (data warehouse)** — олон эх үүсвэрийн түүхэн өгөгдлийг засахгүй, зөвхөн шинжилнэ (A3.4 модульд, HL).

Шийдэхийн өмнө гурван асуулт: (1) апп голдуу уншдаг уу, шинэчилдэг үү? (2) хурдны ашиг илүүдлийн эрсдэлээс их үү — зарим хүснэгтийг л денормчилж болно; (3) хуулбарыг яаж шинэчилж, шалгах вэ (шөнө бүр дахин үүсгэх, шалгалт)?

### 💻 Туршиж үзээрэй

`denormalise.py` 200 000 борлуулалт үүсгээд нэг тайланг хоёр аргаар гаргана. `GROUP BY` ижил хот, ангиллын мөрүүдийг бүлэглэж, `SUM` бүлэг бүрийн нийлбэрийг олно; `ORDER BY 1, 2` эхний хоёр баганаар эрэмбэлнэ (A3.3 модульд дэлгэрэнгүй). `CREATE TABLE … AS SELECT` асуулгын үр дүнгээр шинэ хүснэгт үүсгэнэ. Компьютер дээрээ ажиллуулж үзээрэй (2–5 секунд).

```python
import random, sqlite3, time

random.seed(1)                                   # the same "random" data on every run
con = sqlite3.connect(":memory:")
con.executescript("""
CREATE TABLE Customer (CustomerID INTEGER PRIMARY KEY, City TEXT);
CREATE TABLE Product  (ProductID INTEGER PRIMARY KEY, Category TEXT, Price REAL);
CREATE TABLE Sale     (SaleID INTEGER PRIMARY KEY, CustomerID INTEGER, ProductID INTEGER, Qty INTEGER);
""")
cities = ["Ulaanbaatar", "Darkhan", "Erdenet", "Khovd"]
categories = ["Books", "Food", "Toys", "Tech"]
con.executemany("INSERT INTO Customer VALUES (?, ?)", [(i, random.choice(cities)) for i in range(2000)])
con.executemany("INSERT INTO Product VALUES (?, ?, ?)",
                [(i, random.choice(categories), round(random.uniform(1, 50), 2)) for i in range(300)])
con.executemany("INSERT INTO Sale VALUES (?, ?, ?, ?)",
                [(i, random.randrange(2000), random.randrange(300), random.randint(1, 5)) for i in range(200000)])

# Denormalised copy: everything the report needs in ONE table (City, Category, Price are copied)
con.execute("""CREATE TABLE SaleReport AS
               SELECT Sale.SaleID, Customer.City, Product.Category, Product.Price, Sale.Qty
               FROM Sale JOIN Customer ON Sale.CustomerID = Customer.CustomerID
                         JOIN Product ON Sale.ProductID = Product.ProductID""")

def timed(label, sql):
    start = time.perf_counter()
    rows = con.execute(sql).fetchall()
    print(label, round((time.perf_counter() - start) * 1000), "ms, first row:", rows[0])

timed("Normalised (2 JOINs):", """SELECT Customer.City, Product.Category, ROUND(SUM(Product.Price * Sale.Qty), 2)
    FROM Sale JOIN Customer ON Sale.CustomerID = Customer.CustomerID
              JOIN Product ON Sale.ProductID = Product.ProductID
    GROUP BY Customer.City, Product.Category ORDER BY 1, 2""")
timed("Denormalised (no JOIN):", """SELECT City, Category, ROUND(SUM(Price * Qty), 2)
    FROM SaleReport GROUP BY City, Category ORDER BY 1, 2""")

con.execute("UPDATE Product SET Price = 99 WHERE ProductID = 7")   # the price of redundancy
stale = con.execute("""SELECT COUNT(*) FROM SaleReport WHERE Price <> 99 AND SaleID IN
                       (SELECT SaleID FROM Sale WHERE ProductID = 7)""").fetchone()[0]
print("Product 7: 1 row changed in Product,", stale, "rows in SaleReport are now out of date")
```

Нэг удаагийн гаралт (мс-ийн тоо компьютер, ажиллуулалт бүрт өөр; бусад нь яг ийм):

```text
Normalised (2 JOINs): 122 ms, first row: ('Darkhan', 'Books', 855007.21)
Denormalised (no JOIN): 88 ms, first row: ('Darkhan', 'Books', 855007.21)
Product 7: 1 row changed in Product, 654 rows in SaleReport are now out of date
```

- Хоёр аргын эхний мөр ижил — тайлан нэг; JOIN-гүй нь ихэвчлэн 1.2–2 дахин хурдан. Гурван удаа ажиллуулж, ялагч үргэлж ижил эсэхийг шалга.
- Нэг үнэ өөрчлөхөд SaleReport-ийн 654 мөр хуучирсан: «үнэн» нь Product хүснэгтэд. SaleReport-ийг шөнө бүр дахин үүсгэх эсвэл үнэ өөрчлөгдөх бүрт шинэчлэх механизм хэрэгтэй.
- Кассын систем (бичилт их) нормчилсон хэвээр, сарын тайлан (уншилт их) денормчилсон хуулбараас уншиж болно.

<Callout type="info">
**TOK холбоос.** Сурах бичгийн TOK хэсэг (х.185) utilitarianism-ийн «хамгийн олон хүнд хамгийн их сайн сайхан» зарчмыг асуудаг. Тахлын үед эрүүл мэндийн байгууллага олон хүний хувийн эрүүл мэндийн өгөгдлийг вирусын тархалтыг хянахад шинжилж болох уу, хүмүүсийн тодорхой зөвшөөрөлгүйгээр? Нийгмийн ашгийг хувь хүний эрх, шударга байдалтай хэрхэн тэнцвэржүүлэх вэ? «Хамгийн их сайн сайхан»-ыг хэн тодорхойлох, тооцооноос хэн гадуур үлдэх вэ?
</Callout>

<Callout type="warning">
**⚠️ Анхаарах зүйлс**

- **Денормчлол ≠ нормчлоогүй дизайн.** Эхлээд 3NF хүртэл нормчилж, дараа нь хэмжилтээр үндэслэн санаатайгаар хуулбар нэмнэ.
- **Хуулбарыг шинэчлэх механизмгүй денормчлол = хуучирсан өгөгдөл.** Хариултдаа шинэчлэх арга (шөнийн дахин үүсгэлт, шалгалт) дурд.
- **Бичилт ихтэй, алдаа нь аюултай систем** (банк, эмнэлгийн тун) бараг үргэлж нормчилсон хэвээр байна.
- **Evaluate гэдэг нь жагсаалт биш.** Давуу, сул талаа **энэ** системийн нөхцөлтэй холбож, эцэст нь дүгнэлт гарга.
- **Хурдны тоо зөвхөн жишээ.** SQLite-ийн санах ойд хийсэн хэмжилт; бодит DBMS, бодит өгөгдөлд харьцаа өөр байж болно.

</Callout>

## Дүгнэлт

- **Схем** — өгөгдлийн сангийн дизайн, өгөгдөл биш: ойлголтын (биет, талбар, хамаарал; ERD) → логик (хүснэгт, төрөл, түлхүүр, хязгаарлалт; DBMS-ээс хамааралгүй) → физик (нэг DBMS-ийн бичиглэл, индекс, хэсэглэлт, хадгалалт).
- **ERD:** cardinality — хамгийн ихдээ (нэг эсвэл олон), modality — хамгийн багадаа (0 заавал биш, 1 заавал). Шугамыг нөгөө үзүүрийн тэмдгээр унш; m:m-ийг холбох хүснэгтээр задал.
- **Өгөгдлийн төрөл:** CHAR(n) тогтмол, VARCHAR(n) хувьсах урттай текст, INTEGER, REAL, DATE (`YYYY-MM-DD`), TIME, BOOLEAN. Буруу төрөл → буруу эрэмбэлэлт, нэмэлт хөрвүүлэлт, амжилтгүй оруулалт. Нэг талбар хаана ч нэг төрөлтэй. SQLite төрлийг зөвлөмж гэж үздэг.
- **Түлхүүр:** энгийн, нийлмэл (тусдаа хэд хэдэн талбар), залгасан (нэг талбарт залгасан утга), зохиомол; гадаад түлхүүр байгаа үндсэн түлхүүрийг заана.
- **Нормчлол:** 1NF — түлхүүртэй, давтагдах бүлэггүй, атомар; 2NF — хэсэгчилсэн хамааралгүй; 3NF — дамжсан хамааралгүй. «The key, the whole key, and nothing but the key.»
- **Денормчлол:** уншилт давамгайлсан апп, тайлан, өгөгдлийн агуулахад гүйцэтгэлийн төлөө санаатай илүүдэл; хуулбарыг шинэчлэх механизм заавал.

**Шалгалтад анхаар:**

- **Describe** (A3.2.1): түвшин бүрийг нэрлээд, юу агуулдгийг нэг системийн жишээгээр бич.
- **Construct** (A3.2.2, A3.2.4, A3.2.6): ERD-ийн шугамын хоёр үзүүрийг хоёуланг нь тэмдэглэ; хүснэгт бүрийн `[PK]`, `[FK]`-г тодорхой бич; нормчлолын алхам бүрт аль функциональ хамаарлыг арилгаснаа нэрлэ (*«StudentID → StudentName is a partial dependency»*).
- **Outline** (A3.2.3): төрөл бүрд нэг жишээ талбар; утас, кодыг текстээр хадгал.
- **Explain** (A3.2.5): дүрмийг хэлээд зогсохгүй, өгөгдсөн хүснэгтийн аль талбар яагаад зөрчиж байгааг бич.
- **Evaluate** (A3.2.7): C-S-L-J — уншилт ба бичилтийн харьцаа, давуу тал, эрсдэл, тухайн системд тохирсон дүгнэлт.
- Түгээмэл алдаа: cardinality ба modality-г солих; давтагдсан утга бүрийг 1NF-ийн зөрчил гэх; хэсэгчилсэн ба дамжсан хамаарлыг андуурах; ганц түлхүүртэй хүснэгтийг «автоматаар 3NF» гэх; утасны дугаарыг INTEGER болгох.

**Дараагийн алхам:** доорх «Дасгалууд» хэсэгт 15 дасгал бий — хэсэг бүрд сонгох тест ба код мөшгих нэг нэг, төгсгөлд нь «Normalise the given table to 3NF, showing each step [6]» шалгалтын асуулт. A3 бүлэг A3.3 (SQL) модулиар үргэлжилнэ. A3.2 ба B2.4 нэг алхамд багтдаг тул хамт нээгддэг; дараагийн алхмын модулиуд энэ хоёр модулийн бүх дасгалыг дуусгасны дараа л нээгдэнэ. Амжилт! 🚀
